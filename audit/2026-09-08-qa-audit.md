# QA and software engineering audit — 2026-09-08

Started at `2384976a` (`2026.09.08.8`), working tree clean.

## How this was done

1. **Understand** — 14 parallel readers, one per subsystem, each producing a mechanism map with
   `file:line` citations, an inventory of thresholds, and a list of places where two code paths compute
   the same thing. Those maps drove everything below.
2. **Pass 1** — a systematic sweep across every subsystem, each claim reproduced or refuted by an
   independent checker that had to execute code rather than agree with a reading.
3. **Pass 2** — an adversarial re-read for the bug classes a systematic sweep structurally misses.

## Ground rules for this document

- Every finding names an **input** and the **wrong output** it produces. A claim with neither is not a
  finding and is not listed.
- `[PROVEN]` — I executed the code and watched it produce the wrong value; the evidence is quoted.
  `[TRACED]` — read end to end, not executable in isolation.
- Severity: **P0** data loss, or a wrong number or statement put in front of a human. **P1** wrong
  behaviour, recoverable, nothing bad escapes to a person. **P2** latent: wrong code, currently
  unreachable, or hygiene only.
- Everything fixed was retested before moving on, and where the fix was a behaviour change the fix was
  **reverted again** to confirm the new test actually goes red without it. Those reversion checks are
  recorded.

## The harness built for this audit

`C:\tmp\qa-audit\qaprobe.js` loads the entire application the way `tests/baseline.js` does — every
module plus `script.js` evaluated as one concatenated program against a fake browser — then evaluates
an arbitrary expression **inside that same lexical scope**, so `script.js`'s top-level `let` stores and
helpers are directly callable.

```
node qaprobe.js "out('keys', getWeeklyKeysSorted())"
PROBE_CLOCK=2027-01-01T12:00:00Z node qaprobe.js "..."   # move the calendar
PROBE_TZ=Pacific/Auckland      node qaprobe.js "..."     # move the timezone
PROBE_EMPTY=1                  node qaprobe.js "..."     # load with no data at all
```

This is what makes `[PROVEN]` possible. It lives outside the repo and changes nothing in it.

# Fixed

## S-1 · My Team and My Tips were written to IndexedDB and read from localStorage — `[PROVEN]` · **P0, data loss**

**Where:** `modules/storage.module.js`, `loadTeamMembers` and `loadUserTips`
**Commit:** `83be901b`

`saveTeamMembers` / `saveUserTips` wrote through `saveWithSizeCheck`. `loadTeamMembers` / `loadUserTips`
read `localStorage.getItem` directly. Both keys are in `BULK_STORAGE_KEYS`, so on the IndexedDB backend
the write went to the backend and the read kept looking at a localStorage copy that stopped being
updated at the moment of migration.

Two consequences, both silent:

1. Every team-selection change and every typed tip **appears** to save, because the in-memory copy is
   what the UI renders, and reverts on the next reload.
2. `reclaimLocalStorageCopies` then does the job it exists for, deletes the now-redundant localStorage
   copy, and the loaders return `{}` and `[]` from then on. The team selection and the operator's own
   coaching tips are **gone**, with nothing logged.

**Evidence** — new suite, before the fix, exactly two of seven stores broken:
```
✗ myTeamMembers survives the round trip   expected: "Alyssa Dimes,Chris Vale"  actual: ""
✗ coachingTips survives the round trip    expected: "a tip the operator typed" actual: ""
✗ myTeamMembers: the value is still readable afterwards  expected: "Alyssa Dimes,Chris Vale" actual: ""
✗ coachingTips: the value is still readable afterwards   expected: "a tip the operator typed"  actual: ""
callCenterAverages, callListeningLogs, coachingHistory, ptoTracker, tipUsageHistory — all pass
```

**Why nothing caught it:** `read-chokepoint.test.js` describes this exact failure in its own docstring
and counts four previous occurrences — then exempts `modules/storage.module.js` wholesale, so that
`readStore`'s fallback and the migration read are allowed. The exemption is the right shape and too
wide: it also covered these two ordinary loaders, which are neither.

**Fix:** both read through `readStore`. New `tests/read-chokepoint-storage-module.test.js` asserts
behaviour rather than syntax — for every bulk store the module exposes a load/save pair for, a value
written through the module must read back from the module on the IndexedDB backend, and must survive
reclaiming the localStorage copy. That cannot be satisfied by reading a copy the writes no longer reach,
whatever it is written with.

## S-2 · Five more bulk stores reached around the chokepoint, invisible to both guards — `[PROVEN]` · **P0, data loss**

**Where:** `modules/employee-list.module.js`, `modules/yoy-comparison.module.js`,
`modules/team-scope.module.js`, `script.js` (year-end stores, preferred-name seed, v5 migration)
**Commit:** `f161cd94`

The read and write chokepoint guards both match exactly one spelling:

```js
localStorage.getItem(STORAGE_PREFIX + 'name')
```

Two blind spots in that regex, and both were occupied.

**A renamed prefix.** `employee-list.module.js` took its prefix as an option called `storagePrefix`, so
three raw accesses to `employeePreferredNames` matched neither alternative. `script.js` writes that store
through the module, so the two sides diverged the moment it moved to IndexedDB: rename somebody in
Settings and the rest of the app kept the old name.

**A precomputed constant.** `script.js` declared `YEAR_END_ANNUAL_GOALS_STORAGE_KEY` and
`YEAR_END_DRAFT_STORAGE_KEY` and passed them to `getItem`/`setItem`, so the prefix and the store name were
never adjacent to the call. `yoyBaseline2025` and `employeeSupervisors` had the same shape. The guards
also only inspect `getItem` and `setItem` — which is how a raw **`removeItem`** of `employeeSupervisors`
sat inside the v5 supervisor migration.

All five are `tier: 'data', backend: 'idb'`. So the write never marked the store dirty and never reached
the other machine, and once the store was copied across, `reclaimLocalStorageCopies` deleted the
localStorage copy it believed was redundant and the read returned nothing from then on. **Year-end review
drafts, annual goals and the 2025 baseline all sat behind that.**

Two of them are worse than merely losable:

- `team-scope.getSupervisorMap` is the authoritative answer to "who is on my team". Emptied,
  `resolveMyLabel` returns null and My Team silently falls back to the Settings tick-list — which is
  precisely the disagreement the comment above it says the roster exists to settle
  ("`My Team (8)` against `Scott (10)` in the same table, both of them me").
- The v5 migration's wipe was a **no-op** that can never run again, because it is one-shot and guarded,
  so the voice-dictated v4 assignments the migration exists to remove stayed put.

The preferred-name seed had a third variant: it read and wrote raw at parse time, *after* `hydrate` had
already filled the cache, so the seeded name was written where nothing reads and shout-outs used the
roster first name instead of the one the person actually goes by.

**Fix:** all routed through the module; three now-dead key constants and the dead `storagePrefix`
plumbing removed. New `tests/chokepoint-indirect-keys.test.js` resolves the key instead of matching how
it is spelled — it follows constant aliases, accepts any identifier ending in `prefix`, covers
`removeItem`, and drops identifiers also assigned from `localStorage.key()` so the whole-store sweeps do
not read as offenders. **It found the last two on its own.** It also asserts that it still detects each
shape, because a guard that silently matches nothing is worse than no guard.

## M-1 · Counts were averaged instead of added — `[PROVEN]` · **P1**

**Where:** [script.js:5682](../script.js#L5682) `buildEmployeeAggregateForPeriod`
**Commit:** `d33aeef0`

Every metric except `reliability` was treated as a rate, so `totalCalls` and `transfersCount` were
weighted-averaged **by `totalCalls`**. That is `sum(n·tc)/sum(tc)`, which is not a total or a mean of
anything.

**Repro:** one associate, two weeks — 100 calls with 10 transfers, then 300 calls with 30 transfers.

| | reported | correct |
|---|---|---|
| `totalCalls` | **250** | 400 |
| `transfersCount` | **25** | 40 |
| `reliability` | 5 | 5 ✓ (already cumulative) |
| `aht` | 400 | 400 ✓ (genuinely a rate) |

`250 = (100² + 300²)/400` exactly.

**Reachability, stated honestly:** a weighted mean of one value is that value, and the wow/mom/dod
buckets are single-key (`typedKeys.slice(-1)`), so only a multi-key bucket shows it — the YTD branch, or
any future caller passing two keys. The arithmetic is indefensible under any reading regardless.

**Fix:** the cumulative set is now derived from the registry's `'#'` unit rather than listed, so a count
added later is summed without anyone having to remember that line. Every other aggregator in the app
already sums these (`metric-trends:3467`, `futures:275`, `q1-review:112`).

**Locked by:** a new behaviour-baseline entry over one period, two, six, none, and a key with no data —
the mechanism that exists for `script.js` functions, since the unit suite deliberately does not load
`script.js` as a program. Reverting the fix moves those rows from 1200 to 200 and 66 to 11.

## M-2 · A cell that showed "18.0 hrs" and called it a miss against an 18-hour target — `[PROVEN]` · **P1**

**Where:** [modules/metric-profiles.module.js:120](../modules/metric-profiles.module.js#L120)
**Commit:** `d33aeef0`

`roundToDisplayPrecision` rounded hours to **two** decimals. The app prints hours to **one** —
`formatMetricValue` does `value.toFixed(1)` for `'hrs'` and says so in a comment.

```
18.04  -> prints "18.0 hrs"   meetsYearTarget = false
```

That is exactly the contradiction the function was written to remove. Its own docstring:

> the surface then shows "93.0%" and "below" in the same cell. The reader cannot resolve that, because
> the second decimal is precisely what they were not given.

It survived on the one unit nobody checked — and `display-precision.test.js` **pinned** it: the suite
asserted "hours keep two" and used `18.004` as its probe, which rounds away identically under either
rule.

That suite also hand-copied the formatter it compares against, so a change to the real formatter could
not fail it. `metric-trends` loads cleanly under the harness, so both halves of the pairing now come
from the app.

**Reversion check:** with the fix removed the sweep reports
`no metric disagrees with its own printed value: ["reliability shows 18.0 hrs but reads false"]`.

## C-1 · The raffle believed it was tomorrow from 5pm — `[PROVEN]` · **P1**

**Where:** [modules/contest.module.js:55](../modules/contest.module.js#L55) `todayIso`
**Commit:** `dcd1b023`

"Today" came from `new Date().toISOString().slice(0, 10)` — the **UTC** date. Phoenix is UTC-7, so from
17:00 local onward it is already tomorrow.

That value decides whether a week or a month has **ended**, and the comment beside it is explicit that
neither pays while it is still running: *"Nobody has held a week at target until the week is done."*
From five o'clock on the closing Sunday the week read as finished and handed out its bonus entry, and
from five o'clock on the last day of the month, so did the month.

**Evidence:**
```
UTC 2026-09-09T00:30  ->  local 2026-09-08 17:30 Phoenix,  contest "today" = 2026-09-09
```

`sharedUtils.formatLocalDate` already exists for this and its docstring names the bug
(*"so 'today' can appear as tomorrow's date"*). `todayIso` now uses it.

**Why nothing caught it:** every existing contest test pins `asOf`, which is precisely the branch that
never reads the clock. The new suite pins an **instant** rather than a day, since the whole question is
what happens between local 17:00 and local midnight, and it asserts its timezone pin took effect rather
than passing for the wrong reason.

**Reversion check:** two assertions go red at exactly the Sunday-evening instants.

## D-1 · The "starts on Jan 1, so it is a YTD" rule is dead west of Greenwich — `[PROVEN]` · **P2, latent**

**Where:** [script.js:2374](../script.js#L2374) `detectUploadPeriodTypeByRange`

```js
const start = new Date(startDate);   // bare "YYYY-MM-DD" is UTC midnight
const startMonth = start.getMonth(); // read back in LOCAL time
if (startMonth === 0 && startDay === 1 && daysDiff >= 14) return 'ytd';
```

In Phoenix, `new Date('2026-01-01')` reads back as **31 December 2025**, so the branch never fires.

```
2026-01-01..2026-02-28  days=58   => "week"
2026-01-01..2026-06-21  days=171  => "week"
```

The same probe under `PROBE_TZ=Pacific/Auckland` returns `ytd`, isolating the cause exactly. Note the
second-order effect: with the Jan-1 branch dead, a genuine 171-day year-to-date range falls through
`month` (26–33), through `quarter` (88–95), fails `daysDiff >= 180`, and lands on the `return 'week'`
default. The misclassification is not "YTD read as quarter", it is **"YTD read as a week"**.

**Why it is P2 and not P0:** the only caller immediately discards the result —
`resolveSelectedUploadPeriodType` returns `#uploadPeriodType || detectedPeriodType`, and the upload wizard
writes that hidden input for every selection. It is reachable only through the legacy free-form path,
where an empty `#pasteStartDate` makes `startDate` = `endDate - 6 days`, which never starts on 1 January.

So: wrong code, correct outcome today, one UI change away from silently filing a year of data as a week.

**Recommended fix:** anchor at local noon, the way `parseWeekKeyDate` already does with a comment
explaining why:
```js
const parseLocalNoon = (v) => new Date(/^\d{4}-\d{2}-\d{2}$/.test(v) ? v + 'T12:00:00' : v);
```
**Not fixed** because it is a behaviour change on the upload path with no current caller, and it belongs
with a decision about whether the legacy path should exist at all.

## M-3 · The employee aggregate still accepts overlapping periods — `[PROVEN]` · **P1**

**Where:** [script.js:5682](../script.js#L5682)

The count half of this is fixed. The overlap half is not: `reliability` is summed across every period key
handed in, with no guard.

```
one YTD snapshot for 2026   -> reliability 4   (correct)
two YTD snapshots for 2026  -> reliability 8   (100% inflation)
```

`getTrendComparisonBuckets(keys, 'ytd')` buckets YTD keys **by year** and hands the whole bucket in as
`currentKeys` — it does not pick one. Reliability is measured in hours against a hard 18-hour ceiling and
is one of the five metrics scored at year-end.

`cleanupStaleDuplicatePeriods` keeps only the newest **real** YTD per year and runs at boot, which is why
this is not already visible — but it returns early on `autoGeneratedYtd`, and `cleanupStaleAutoYtds` only
removes auto-YTDs for a year that already has a real one. Whether a reachable state survives both
cleanups is under verification.

The defect stands regardless of that: **the aggregator accepts overlapping periods and silently produces
a wrong cumulative total.**

# Refuted

A refuted claim is a result, and both of these looked serious enough to be worth recording so nobody
re-opens them.

## R-1 · "The celebration target gate opens on 1 January 2027" — **refuted**

`metric-profiles` genuinely has no targets or rating bands past 2026, and `getYearTarget(k, 2027)` returns
`null` for every metric. But `meetsCelebrationTarget` falls back to
`window.METRICS_REGISTRY[...].target`, the year-less registry value, so the gate still closes:

```
adherence=70       2026=false  2027=false
associateOverall=50 2026=false  2027=false
reliability=90     2026=false  2027=false
```

`calculateYearEndOnOffMirror` is likewise safe in 2027 — it scores 1 across the board and returns
"Off Track", because `on-off-tracker` carries its own band copy.

What **is** true and worth a decision before January: 2027 data will be silently judged against 2026
targets, and `getRatingScore` / `getRatingBandRowColor` return `null` in 2027 so score cells and their
colours go blank. That is a data-entry task, not a code defect.

## R-2 · "Three metrics pass the celebration gate on failing numbers today" — **my own error, refuted**

My first probe passed registry keys (`scheduleAdherence`, `cxRepOverall`, `overallSentiment`) to
`meetsCelebrationTarget`. That table is keyed by celebration-local ids (`adherence`, `associateOverall`,
`sentiment`), so unknown keys correctly took the documented "an unjudgeable metric is left alone" branch,
which `celebrations-scope.test.js:69` pins. Called with the ids its callers actually use, the gate is
correct on every metric.

# Verified clean

Recorded because these are the scenarios most likely to be broken, and they are not.

**Empty-state boot.** Loaded with no `weeklyData`, no `ytdData`, no `dailyData`, no team members — the
state after Settings → Delete Data, or a first-ever load — and drove the real boot path plus all seven
section initializers and 27 top-level render functions. `errors: []`. Nothing throws.

**Clock sweep.** The suite was run at seven dates to separate application date bugs from fixture
artifacts. After T-1, zero failures at every one. The 2026-01-01 / 2026-02-28 mass failure is a fixture
artifact, not an application bug: the fixture's data is dated mid-2026, so at a January clock the whole
dataset is in the future. Diffing assertion labels between 2026-08-18 and 2027-01-01 confirms the suite
degrades *cleanly* — the affected suites report `skipped — the current month has no complete pair behind
it this year` rather than asserting wrongly.

**Store registry drift.** The registry's 37 `backend: 'idb'` names and the hand-written fallback in
`constants.module.js` agree exactly, in both directions.

**Celebrations fallback writes.** `celebrations.saveHistory` and `readViaStorage` do use raw localStorage,
but only after trying the storage module first — the correct "module not loaded yet" shape, and the same
allowance `read-chokepoint.test.js` makes.
